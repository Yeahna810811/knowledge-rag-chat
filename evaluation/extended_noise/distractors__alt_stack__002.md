536 维。
它的优点是 API 稳定、无需本地部署；缺点是数据要出网，且按 token 计费。

中文开源方案里，m3e-base 和 bce-embedding-base-v1 也是常见选择，两者均为 768 维，
在中文语义相似度任务上的表现各有胜负。选型时不能只看公开的榜单分数，
必须在自己的业务语料上做召回评测——公开榜单的分布和你的真实提问分布
往往差异很大。

## 文本切分策略

按段落递归切分是最朴素的做法，但在技术文档上效果一般。更好的方式是
MarkdownHeaderTextSplitter，按标题层级把文档切成语义完整的块，
并把上级标题作为元数据一起保留，检索时把这些标题拼回 chunk 里，
可以显著改善「这个配置属于哪个模块」这类问题的召回。

还有一种做法是基于语义的切分：先用嵌入模型给相邻句子算相似度，
在相似度显著下降的地方断开。它切出来的块语义更完整，但计算开销大，
且切分结果不稳定——同一份文档改一个字，切分边界可能整体漂移。
