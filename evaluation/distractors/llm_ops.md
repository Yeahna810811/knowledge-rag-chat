# 大模型选型与成本控制（干扰语料，与本项目无关）

说明：本文档是干扰语料，描述一套假想系统的选型记录，不代表本项目现状。

## 模型能力对比

在需要复杂推理的任务上，GPT-4o 和 Claude Opus 仍然领先开源模型一截，
尤其是多步推理、指令遵循和长上下文理解。但它们的单价较高，
在问答这种高频短请求场景里，成本会快速累积。

国产模型里，DeepSeek-V3 在代码和数学上表现突出，且 API 价格显著低于同级别
闭源模型；Qwen 系列的中英双语能力均衡，生态工具链完善。选型的实践经验是：
先用最强的模型把 prompt 和业务效果调到位，再逐级降配到更便宜的模型，
每一步都用同一份评测集验证效果损失，而不是一上来就为了省钱选小模型。

## 上下文窗口与长文档

长上下文模型（128K 甚至 1M）看起来可以「把整本书塞进去」，但实际使用中有两个坑：
一是注意力衰减，模型对位于上下文中部的内容关注度明显低于开头和结尾；
二是成本和延迟随长度线性增长。所以长上下文并不能替代检索,
它更适合「已经定位到少量候选文档之后」的精读阶段。

一个务实的折中是：检索召回 20 个候选块，重排后取 5 个拼进上下文，
这样既保证信息覆盖，又把输入 token 控制在几千级别。

## Prompt 工程要点

系统提示词应当明确三件事：角色、可用信息边界、输出格式。其中「信息边界」
最关键——要明确告诉模型「只能使用提供的参考资料，资料里没有就说不知道」，
并且给出拒绝回答时的标准话术模板。不给拒绝话术的模型，
在资料缺失时倾向于编造一个看起来合理的答案。

温度参数在问答场景建议设为 0 或接近 0，保证同一问题的答案可复现；
在需要创意生成（比如营销文案）的场景再调高到 0.7 以上。

少样本示例（few-shot）对小模型的提升比大模型明显。如果降配到小模型后
输出格式不稳定，优先加 2 到 3 个输入输出示例，而不是堆砌指令文字。

## 成本与延迟控制

生产环境的成本控制主要靠三招：缓存、批处理、降级。
对高频重复问题做答案缓存，命中率通常能到 20% 到 40%；
批量请求合并可以减少网络往返；降级是指在主模型超时或超预算时
自动切换到更便宜的模型，并记录降级次数作为监控指标。

流式输出对用户体验的改善大于对延迟的改善——首字时间（TTFT）才是
用户感知到的「快慢」，总耗时用户在流式场景下反而不敏感。
