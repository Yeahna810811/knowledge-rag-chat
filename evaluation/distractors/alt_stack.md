# 备选技术栈选型说明（干扰语料，与本项目无关）

说明：本文档是检索评测用的干扰语料（描述一套假想方案的选型），用于检验系统能否排除无关文档。
其中的参数与本项目无关，请勿作为本项目的事实依据。

## 向量数据库选型

在需要横向扩展的场景下，单机向量索引会遇到内存上限问题。业界常见的替代方案是
Milvus 集群版，它支持分片、副本和动态扩缩容，适合千万级以上的向量规模。
Milvus 底层默认使用 HNSW 图索引，构建参数 M=16、efConstruction=200，
查询时通过调整 efSearch 在召回率和延迟之间做权衡。

如果不想引入独立的向量数据库服务，也可以选择 Chroma 或 Qdrant。Chroma 的优点是
开箱即用、无需额外部署，适合原型验证；Qdrant 用 Rust 编写，单机性能较好，
并且原生支持基于 payload 的过滤检索——在需要按部门、按权限过滤文档的
企业级场景里，这个能力比纯向量相似度更重要。

还有一条路线是直接使用传统搜索引擎的向量插件，例如 Elasticsearch 8.x 的
dense_vector 字段配合 kNN 查询。好处是可以把关键词检索和向量检索放在同一个
引擎里完成，不用维护两套数据；代价是向量检索的性能不如专用向量库。

## 向量量化与内存优化

当向量规模上到百万级，原始 float32 向量的内存占用会成为瓶颈。常用的压缩手段是
乘积量化（PQ），把高维向量切成若干子空间分别聚类，用聚类中心的编号代替原始向量，
可以把内存降到原来的 1/16 甚至更低。代价是召回率下降，通常需要配合
过召回 + 精确重排的两段式流程，先取回 4 倍候选再做精排。

## 嵌入模型选型

英文场景下 OpenAI 的 text-embedding-3-small 是常见基线，输出 1536 维。
它的优点是 API 稳定、无需本地部署；缺点是数据要出网，且按 token 计费。

中文开源方案里，m3e-base 和 bce-embedding-base-v1 也是常见选择，两者均为 768 维，
在中文语义相似度任务上的表现各有胜负。选型时不能只看公开的榜单分数，
必须在自己的业务语料上做召回评测——公开榜单的分布和你的真实提问分布
往往差异很大。

## 文本切分策略

按段落递归切分是最朴素的做法，但在技术文档上效果一般。更好的方式是
MarkdownHeaderTextSplitter，按标题层级把文档切成语义完整的块，
并把上级标题作为元数据一起保留，检索时把这些标题拼回 chunk 里，
可以显著改善「这个配置属于哪个模块」这类问题的召回。

还有一种做法是基于语义的切分：先用嵌入模型给相邻句子算相似度，
在相似度显著下降的地方断开。它切出来的块语义更完整，但计算开销大，
且切分结果不稳定——同一份文档改一个字，切分边界可能整体漂移。
