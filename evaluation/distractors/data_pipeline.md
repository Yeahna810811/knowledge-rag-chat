# 数据处理与同步管道（另一个项目的工程文档）

说明：本文档是干扰语料，与本项目的数据流无关。

## 数据接入

知识库的源头数据通常散落在各处：对象存储里的 PDF、
数据库里的结构化记录、内部 wiki、以及第三方系统的 API。
接入层要做的第一件事是统一抽象成「文档 + 元数据」，
后续所有处理都只面向这个抽象。

增量同步比全量同步复杂得多。全量可以每天跑一次，
增量需要识别新增、修改、删除三类变更。
删除最难处理——源系统往往不给删除事件，只能靠定期全量比对。

## 数据清洗

原始文档里充满噪声：页眉页脚、水印文字、目录页、
扫描件识别出的乱码。清洗规则要根据文档类型定制，
但有几条通用规则：去掉重复行、合并被错误断行的段落、
删除只有一个字符的行。

表格和图片是最难处理的部分。表格被转成纯文本后行列关系丢失，
建议转成 Markdown 表格或结构化 JSON 单独存储。
图片如果只是装饰可以丢弃，如果包含信息则需要 OCR 或多模态模型生成描述。

## 调度与重试

任务调度要考虑依赖、并发、重试三件事。依赖用有向无环图表达，
并发要限制在下游能承受的范围内，重试必须区分错误类型——
网络超时可以重试，参数错误重试一万次也没用。

重试策略建议用指数退避加抖动。固定间隔重试会造成重试风暴：
一批任务同时失败又同时重试，把已经很脆弱的下游彻底打垮。

## 幂等性

管道里的每个环节都应该是幂等的：同样的输入执行多次，
结果完全一致。这对向量入库尤其重要——
重复入库同一文档会产生重复向量，检索时同一个内容出现多次，
挤占宝贵的上下文窗口。

实现幂等的常见手段是给每个文档计算内容哈希，
入库前先查哈希是否存在。注意哈希要在清洗之后计算，
否则格式微调会导致哈希变化、触发不必要的重建。
