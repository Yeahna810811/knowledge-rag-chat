# 高级检索技巧综述（通用技术资料，非本项目现状）

说明：本文档是通用技术资料，用作评测的干扰语料。

## 查询改写

用户提问往往是口语化、指代不完整的。多轮对话里尤其明显——
用户问「那它的参数是多少」，单独看这句话完全无法检索。
常见做法是用一个小模型把当前问题结合历史对话改写成独立完整的查询，
这一步叫 query rewriting 或者 contextual compression。

另一个方向是 HyDE：先让模型针对问题生成一个「假想的答案」，
再用这个假想答案去检索。因为假想答案的表述风格更接近文档，
检索效果有时反而比用原始问题更好。代价是多一次模型调用。

## 多路召回与融合

单一检索路线的覆盖面有限。把关键词检索和向量检索的结果合并，
是工业界的常见做法。合并时不能直接用原始分数相加——
两种分数的量纲完全不同，直接相加等于让其中一路主导结果。
用倒数排名融合（RRF）可以规避这个问题，它只看排名不看分数，
公式里的常数 k 控制头部排名的权重，通常取 60。

## 结果重排

召回阶段为了速度，query 和 doc 是分别独立编码的，两者没有交互。
重排阶段把 top-N 候选拿出来，用交叉编码器把 query 和 doc 拼在一起
过一遍模型，精度更高但慢得多。所以重排只对少量候选做，
通常是「召回 50 到 100，重排后取 5」。

需要注意重排模型的语言必须与语料匹配。用只在英文上训练的重排模型
处理中文文档，效果可能还不如不重排。

## 表格与图片

技术文档里的关键信息经常在表格里，而表格被切分后行与列的对应关系会丢失。
常见处理是把表格整体转成 Markdown 文本或者自然语言描述后再入库，
并在元数据里标记它来自表格，检索时可以适当加权。

图片的处理更麻烦：需要先 OCR 或者用多模态模型生成描述，
再把描述文本入库。直接把图片丢给嵌入模型，得到的向量语义不可控。

## 评测方法论

检索评测要区分「能不能召回」和「排在第几位」。
召回率（Recall@K）只看前 K 个里有没有，命中率上去了不代表排序好；
MRR 和 NDCG 才反映排序质量。只看单一指标容易得出错误结论。

还有一点常被忽略：评测集必须包含难负样本。如果语料里只有互相无关的文档，
随便一个检索器都能拿高分，这样的评测结果没有参考价值。
