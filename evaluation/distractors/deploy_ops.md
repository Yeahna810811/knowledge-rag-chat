# 部署与可观测性实践（干扰语料，与本项目无关）

说明：本文档为干扰语料，描述一套假想系统的部署方式，用于检验检索抗干扰能力。

## 容器编排

单机部署用 docker compose 足够，配置文件里要显式声明健康检查，
否则容器进程还活着、但服务已经不可用的时候，编排工具不会自动重启它。
健康检查建议直接打业务接口而不是只做端口探测。

需要多实例和滚动更新时再上 Kubernetes。K8s 的 Deployment 负责副本管理，
Service 负责服务发现，Ingress 负责外部流量入口，ConfigMap 和 Secret
分别管理非敏感配置和敏感凭据。Secret 默认只是 base64 编码，不是加密，
生产环境应当配合外部的密钥管理服务。

资源限制（requests 和 limits）必须设置。不设 limits 的话，
一个内存泄漏的 Pod 可以把整个节点的内存吃光，导致同节点上的其它服务一起被驱逐。

## 网关与限流

对外暴露 API 时，网关层要统一处理认证、限流、日志和熔断。
限流建议按用户维度而不是按 IP 维度——多个用户共用出口 IP 的场景下，
按 IP 限流会误伤正常用户。

熔断的目标是防止下游故障向上游传导。当依赖的大模型 API 连续失败时，
快速失败并返回降级答案，比让用户一直转圈要好。熔断器的三个状态
（关闭、打开、半开）里，半开状态的探测策略最容易写错：
必须在半开状态限制放行流量，否则一恢复就把下游再次打垮。

## 可观测性三件套

日志、指标、链路追踪。日志要用结构化格式（JSON），并带上统一的
请求 ID，否则跨服务排障时无法把一次请求的日志串起来。

指标方面，除了 CPU、内存这类基础指标，业务指标更有价值：
问答接口的 P95 延迟、检索命中率、模型调用失败率、平均召回块数。
其中「平均召回块数」如果被塞满了上限，说明 top_k 设小了；
如果长期远小于上限，说明知识库覆盖不足。

链路追踪在 LLM 应用里尤其重要，因为一次问答会经过检索、重排、生成、
后处理多个阶段，只看总延迟无法定位是哪一段慢。给每个阶段打 span，
能直接看出「慢在检索还是慢在生成」。

## 日志脱敏

用户提问和模型输出都可能包含敏感信息。落日志前必须做脱敏处理，
手机号、身份证、邮箱、密钥都要打码。这一条在金融和医疗场景下是合规硬要求，
不是可选的优化项。
